# Account data export and deletion (RUN-51)

## Owner workflow

In **Settings → Account & data**, choose **Download account data** before deletion if you need a copy. `GET /api/account/export` uses the verified session's owner; it accepts no target user ID. ADMIN has the same personal-data boundary as USER. The attachment is a versioned private JSON archive, separate from the privacy-filtered AI planning export. Do not send this account archive to an AI service.

Version 1 contains the account and registration profile, athlete profile, body measurements, goals, drafts, issued AI-request snapshots, plans and all approved revisions/workouts, reminder state, activity summaries/laps/duplicate candidates, normalized health and allowlisted Garmin health metrics, integration metadata, safe sync summaries and publication/attempt history. Dates use ISO 8601; Prisma decimal values and 64-bit integers use decimal strings. The database read uses a repeatable-read transaction; no partial archive is sent if reading fails. The completed snapshot is streamed as an attachment. Large accounts still require server memory and must complete the read within 30 seconds; a timeout returns 503 and can be retried. This is a data portability archive, not an application restore/import format.

Passwords/hashes, authentication accounts/tokens, session cookies/IP addresses, encrypted provider credentials, encryption keys/versions/nonces, internal leases/checkpoints/rate-limit records, raw untrusted metadata, private asset references and other users' data are excluded. Garmin's retained numeric health projections are re-allowlisted on export. User-authored text remains user data; do not paste secrets into goals, names or plan notes. Authentication operational logs are not part of the archive.

Choose **Delete account**, review the consequences, confirm provider revocation and type **DELETE**. The same-origin `DELETE /api/account` body is exactly `{ "confirmation": "DELETE", "providerAccessRevoked": true }`; extra fields, including an owner ID, are rejected. Origin and current active session are checked on the server. This is an irreversible, explicit account action.

## Provider revocation before deletion

The implemented Garmin, Intervals.icu and optional OpenAI connections store personal API keys. There is no implemented remote revocation adapter. Before confirming deletion:

1. Revoke/regenerate every key saved here in the issuing Garmin Personal API account, Intervals.icu Developer Settings and OpenAI API key settings. An OpenAI key may exist from earlier configuration even though automatic generation is Post-MVP. An account that never saved keys may confirm that fact instead.
2. Remove published events directly in Intervals.icu/Garmin Connect and on devices if desired. Disable Intervals.icu's forwarding to Garmin if desired. Local account deletion does not erase provider accounts, published events or watch history. Remote work already accepted by a provider cannot be recalled by deleting local rows.
3. Close other app tabs and wait for sync/publication to finish. The app refuses deletion with 409 while a sync cursor or publication has an unexpired lease; wait and retry. Provider-side revocation also prevents an already authenticated in-flight request from retaining future access. A provider may have accepted a request before revocation; inspect its calendar/history separately.

The checkbox records the user's attestation, not verified provider revocation. No success message claims remote access was revoked by the app. Never delay local data removal on provider availability after the user has completed this flow. If revocation is inaccessible, the operator should help the owner regain provider access before confirmation; do not enter or transmit keys in support messages. Future OAuth integrations must add a bounded, retryable revocation adapter and recovery state before enabling that auth method; deleting token rows alone is not remote OAuth revocation.

## Atomic removal and failure behavior

Deletion locks the auth identity, application identity and provider connections, checks leases, marks the owner `DELETING`, writes a minimal deletion receipt, then deletes the application and Better Auth identities in one transaction. Foreign-key cascades remove profile/measurements, goals/drafts/issued requests, immutable approved plan revisions/membership, workouts/reminders, activities/laps/duplicates, health, connections/encrypted keys, sync runs/checkpoints, import rate limits, publication attempts and sessions/password credentials. Exact email verification identifiers and any outstanding invitation claim linked by the auth user's claim nonce are also removed. Completed invitations already have their claimed email/nonce cleared; anonymous invitation/rate-limit records are shared operational state and are not deleted by matching arbitrary user input or an email substring.

There is no queue or Cron. Current MVP has no persisted Web Push subscriptions, notification-delivery store or app-managed FIT/GPS object store: uploads are processed without retaining private files; existing activity asset references are metadata, not managed object copies. There are no push tokens to revoke. Before introducing these stores, add owner cascades and actual external-object deletion/export coverage to this flow. The account operation must not claim to erase an external file merely because its reference disappeared.

The existing snapshot triggers permit deletion only through the account cascade; regular approved-history mutation remains blocked. Provisioning locks the Better Auth identity so a session read before deletion cannot recreate a deleted application identity. Old sessions fail after commit. A failure, including failure to append the receipt or a database constraint error, rolls back the entire operation. No half-deleted account is committed, and retry is safe. If the HTTP response is lost after commit, reloading/sign-in confirms the session is invalid; the deleted account has no recovery or undo. A new account requires a new invitation and does not recover old data. After success, a full navigation to sign-in discards the current tab's private router state. Previously downloaded exports and data already displayed in another tab/device remain under the user's control.

## Safe audit evidence and retention

`account_deletion_receipts` retains only the deleted internal UUID, SHA-256 of the opaque auth subject, deletion time and expiration time (90 days). The table itself denotes the `ACCOUNT_DELETED` event; it contains no email, health details, tokens, provider account IDs or error payloads. These are pseudonymous recovery identifiers, not anonymous data. They survive account cascades and are available only to trusted operators; there is no admin API listing them. Runtime has SELECT/INSERT, with no UPDATE/DELETE/TRUNCATE grant. Do not log account archives or raw failures. No new persistent HTTP audit log is introduced.

Operators purge expired receipts daily using the migration/direct role and `prisma/scripts/prune-account-deletion-receipts.sql`. Confirm the target with `pnpm db:assert:development` or `pnpm db:assert:production`, then run `pnpm exec prisma db execute --schema prisma/scripts/direct.prisma --file prisma/scripts/prune-account-deletion-receipts.sql`. Check deletion counts privately; alert operationally if the daily task is missed. This is an operator duty, not an app-scheduled job. Protect any exported recovery receipts equivalently and destroy them at their expiration.

Personal records are retained until owner deletion in this MVP; no separate raw FIT archive or provider debug payload is retained. Minimal platform request logs follow the hosting provider's configured retention, must exclude request/response bodies and secrets, and need their own verified deletion/access settings at launch. The 90-day receipt policy does not authorize retaining personal archives or debug payloads for 90 days.

## Backups and restore after deletion

The deployment policy is **at most 30 days** for every database backup/PITR window and independently retained copies. This is a required operator configuration, not a claim that the current Neon plan or exports have been verified. Before release, inventory Neon recovery windows/branches, manual dumps, local copies, hosting logs and historical keys; record actual settings and verify they meet the limit. If they cannot, correct the configuration and user-facing policy before enabling deletion in that environment. Deletion removes live rows immediately; older backups may retain data until expiry. Do not promise selective physical erasure from immutable provider backups. Never copy personal production data into Preview.

1. Before any restore, preserve the **latest** unexpired deletion receipts outside the database being restored in protected operator storage. A backup taken before deletion does not contain its receipt. If the live DB is unavailable, use the separately protected deletion-receipt copy. Maintain that copy daily and after confirmed deletions; reconcile it before opening a restored service. If current evidence is unavailable or incomplete, keep the restored service offline until deletion requests are reconciled with owners/operators. Receipt copies contain pseudonymous personal data and expire with the source records.
2. Restore into a private, offline target using the matching historical encryption keys. Apply current migrations. Merge the latest receipts, preserving original deletion/expiry times; do not extend retention. Stage the latest receipts in the restored `account_deletion_receipts` table. Do not attach public Preview deployments or run provider sync/publication during recovery.
3. Run `prisma/scripts/replay-account-deletions.sql` using the direct migration role. It matches both internal UUID and auth-subject hash before deleting application data, then deletes matching auth identities and associated verification/claim records. Cascades remove restored credentials and sessions. A newly invited account with a new identity is unaffected. Replaying is idempotent. Check counts and verify that receipt-matched users, auth accounts, credentials and health no longer exist.
4. Invalidate all remaining restored sessions, rotate authentication/deployment secrets as appropriate and verify ownership before reopening. Test a synthetic deleted owner and a surviving owner. Reconfirm external revocation; a backup must never re-enable a revoked key. Do not reconstruct removed data from exports without a new explicit owner request and supported import flow.
5. Purge expired database branches/dumps/receipt copies and historical key versions after their configured windows. Document the restore point, receipt reconciliation and synthetic checks without athlete content. RUN-53 owns deployment-specific backup verification and release evidence; this issue does not certify Production or a completed restore drill there.

## Migration and rotation handoff

The RUN-51 migration only adds the small receipt table and expiry index; it does not transform or delete existing data. Apply migrations, run `pnpm db:grant:runtime`, regenerate Prisma and deploy application code in that order. Follow the environment guards in [database operations](database-operations.md). Test fresh migration application and seeded owner deletion on an isolated database. Roll back application code if needed; keep the additive table and its evidence. Never roll back a completed deletion by restoring old rows.

For vault key rotation, follow [provider credential operations](provider-credential-operations.md#rotate-vault-encryption-keys): keep old and new versions, deploy the new active version everywhere, verify the deployed/database-bound key proof, run `credentials:rotate --check`, `--apply`, then `--check`; verify zero old rows before retiring online keys. Keep historical backup keys only for still-retained backups, then destroy both. On compromise, rotating encryption alone does not revoke exposed provider keys: owners must revoke/regenerate them, invalidate sessions if affected and reconnect with new keys. Stop publication/sync while investigating. A failed row/proof check stops key retirement; retain old keys and retry safely after fixing the cause. Never log plaintext, keys, connection URLs or athlete payloads.
