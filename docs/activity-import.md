# RUN-24: completed activity import

`POST /api/activities/import` accepts `{ "date": "YYYY-MM-DD", "start": 0 }` from an authenticated account with a connected Garmin key. JSON request bodies are capped at 1 KiB; larger bodies return HTTP 413 before the per-owner rate limit is consumed. The selected Garmin local calendar date is bounded to eight days before or one day after the current UTC date, allowing global timezone boundaries. One request reads at most three activity details and their FIT downloads. A shared database limit accepts at most three import requests per owner in each 60-second window; additional requests return HTTP 429 before contacting Garmin. A `429` from any Garmin endpoint stops the current page and returns `RATE_LIMITED` with HTTP 429. If FIT was rate-limited, the already verified JSON activity is saved without new laps before stopping. A later request may safely repeat the page because saved activities are upserted. `start` is a bounded search offset (0–300); `nextStart` points to the next page when `hasMore` is true. There is no scheduler, durable checkpoint, historical backfill, upload, or retry orchestration.

The route derives the owner from the verified session, reads only that owner's encrypted Garmin key, and uses one token for the owner-scoped search, detail and FIT requests. List and detail IDs must agree. The RUN-23 normalizer checks FIT Session identity against JSON before any lap is saved. Missing FIT or unusable Lap data still allows a verified JSON activity to be saved without new laps. Corrupt FIT, mismatched Session identity, and invalid activity JSON fail before that activity is written. Responses never contain provider credentials, bearer tokens, raw JSON, FIT bytes, or private object references.

`src/server/activity/import.ts` accepts validated canonical activities with owner/provider/external-ID identity. A serializable transaction upserts the activity and refreshes owner-scoped cross-provider duplicate review candidates. `lapIndex` is display order. When replacing laps, the importer preserves an existing lap ID only for an unambiguous match on source record type and start instant; inserted earlier laps cannot take another lap's ID. `IMPORTED` means the supplied FIT yielded validated laps. If FIT is unavailable and the canonical JSON summary is unchanged, prior verified laps remain with `RETAINED` status. If the summary changed, old laps are cleared and status becomes `UNAVAILABLE`. A stored source observation time stops an earlier detail response from overwriting a later one after concurrent fetches; Garmin's provider modification version is not yet verified. Near matches are review candidates only; no activities are merged or deleted. Downstream analytics must choose an authoritative source or exclude unresolved candidates before summing activities.

`GET /api/activities?limit=20&cursor=<opaque-cursor>` returns an owner-scoped page, ordered by the activity's initial start instant and ID descending. This immutable list key is set on first import and remains fixed when the provider later corrects the current start instant. The owner-bound cursor carries that stable page boundary, preventing skipped or repeated rows when an already-listed activity changes. `GET /api/activities/<id>` returns only the owner row and ordered laps. An ADMIN has the same owner boundary as a USER. Both reads expose duplicate candidate IDs for review and use `Cache-Control: private, no-store`. Raw object and GPS asset references remain private database fields and are omitted from responses.

The athlete can add, replace, or remove their own Garmin Personal API key in `/app/settings`. The owner-scoped `/api/integrations/garmin` endpoint stores the key encrypted and returns connection metadata only. Settings report `KEY_SAVED` after storage, `CONNECTED` after a successful Garmin activity search, and `ERROR` after a `401` from the token endpoint rejects the saved key. A failed request for an older key cannot change a replacement key's status. A `403` from the token endpoint or a later denial from the activity API returns `ACCESS_DENIED` without claiming that the key itself was rejected. Garmin does not supply a reliable expiry reason in this flow, so an authorization rejection is not labeled `EXPIRED`. An import exchanges the stored key for a short-lived bearer token; neither key nor token is sent back to the browser after saving. OpenAI key creation is unavailable until automatic plan generation is implemented; previously stored OpenAI keys can still be removed.

## Migration and verification

The `20261108_run24_activity_import` migration widens existing integer distance to decimal meters, adds nullable canonical fields and source observation time plus lap status, backfills an immutable list start instant, and replaces the activity list index. It also creates owner-compatible lap and duplicate-candidate tables with foreign keys and uniqueness, plus a per-user Garmin import counter with a cascading user foreign key. It removes legacy Garmin keys from the shared auth rate-limit table, resetting any in-progress import limit window during the cutover. The activity table update and index replacement can briefly lock activity writes. The migration does not delete activity data. Apply only after verifying the development target with `pnpm db:assert:development`; then run `pnpm db:migrate` and `pnpm db:grant:runtime` with the migration role. Validate on a fresh isolated database and run `pnpm test:db`. Deploy application code only after this migration. For recovery, stop writes and restore the matching Neon branch/PITR and app version; there is no automatic down migration. Production migration and deployment remain operator actions.
