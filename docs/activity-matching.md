# Completed activity matching (RUN-42)

Open a saved Garmin activity from Training History or the calendar, then select **Match planned session**. Matching reads persisted canonical Activities and approved local workouts. It does not call Garmin or Intervals.icu, start sync, publish workouts, or require a live provider connection. Stored Garmin account visibility rules still apply; replacing the connected Garmin account does not expose the previous account's records.

The review screen suggests a session only when exactly one compatible session shares the activity's date in the **session timezone**, at least one complete duration/distance estimate agrees within 25%, and no duplicate record is flagged. Multiple sessions on the same local date stay ambiguous even if one has closer metrics. Every association, including a single suggestion, requires **Confirm link**. The athlete-local activity date uses the profile timezone, then recorded timezone, then UTC. The activity start timestamp is also shown in UTC; the canonical workout has a local date rather than a prescribed start time. No precise time-of-day match or unreliable provider-title hint is invented. Existing publication metadata is optional and is not needed for this flow.

Manual override lists compatible, unlinked workouts within seven days of the selected search date. Change that date to find a session elsewhere. Canceled sessions and unknown `OTHER` sports cannot be linked. One activity links to at most one logical workout, and one workout to at most one activity. **Confirm relink** moves the association atomically; **Unlink activity** removes it. History locks remain permanent on the previous prescription, while its match-derived completion outcome is removed. Explicit manual completions remain completed after unlinking. A duplicate warning lists visible, owner-scoped blocking associations with **Unlink duplicate activity**, including legacy Intervals.icu/file/manual records; those records do not become new inbound activity sources or new matching candidates.

Server actions derive the owner from a verified session and check the activity, plan, current approved revision and nested workout. Mutations use serializable transactions, compare the expected current revision and existing link, and touch the plan to serialize with refresh and reschedule. A flagged duplicate graph is checked transitively: if another record in that group is linked, the mutation fails. A duplicate record may be manually selected after unlinking the previously used record. Concurrent linking cannot count both records.

## Comparisons and preservation

`PlannedWorkout.completedRevisionId` pins the approved prescription chosen at confirmation. Definition, local date and timezone come from that immutable revision membership. The activity link uses the stable internal Activity ID, so summary/FIT reimports enrich actual metrics without recreating the association. New plan revisions and changes to other scheduled sessions do not change the pinned comparison. Garmin disconnect keeps the saved activity and its link. Explicit **Delete imported Garmin data** clears associations before deleting the records, preserving plan history locks.

Planned distance and duration use the canonical step/repeat estimator; open or incompletely specified totals remain visibly incomplete. Pace and heart rate targets are labeled step ranges, not invented session averages. Actual distance is stored meters and duration is stored timer milliseconds converted to seconds. Pace uses timer seconds per kilometer from saved distance, falling back to `1000 / avgSpeedMps` for positive recorded average speed when timer/distance cannot supply pace. The screen labels the pace source for activities and laps. Missing timer, distance, heart rate or laps remain unavailable; recorded speed never invents duration or distance. Elapsed/moving time is never silently substituted for timer time. Laps show saved metrics and `FIT_LAP` provenance without assuming alignment to planned steps. Incompatible sports suppress comparison metrics.

`completedAt` remains the immutable first completion/history marker. `completionFromActivity` identifies matching-derived outcomes, and `completionAt` records the current completion date. Calendar and AI commitment exports use the current outcome rather than interpreting the first marker as proof of completion. Unlink/relink clears the old matching-derived outcome and keeps its locks. A replacement activity supplies its own completion date. Explicit manual confirmation stores an independent outcome, so unlinking its optional activity does not revoke it. AI response preview checks the same projected completion date to reject evidence exported before a correction.

Accepted reimports synchronize an active match-derived completion date with the stored activity start in the same serializable transaction. This includes summary-only reimports and repairs an already-stale derived date even when the activity itself is unchanged. Older provider observations are rejected before either update. Manual completions, withdrawn associations, other owners, immutable first markers, locks and pinned approved revisions remain unchanged; a later failed lap write rolls the activity and completion correction back together.

## Migration and rollout

Apply the single RUN-42 migration, `20261116140000_run42_activity_matching`, before deploying the new client/application. It adds a nullable UUID and an owner/plan-compatible foreign key to approved revisions, a check preventing a comparison reference without an activity, and current completion date/source fields with a consistency check. It retains immutable markers and locks. All constraints are created before backfills queue deferred foreign-key checks. No credentials, new provider contract, table, background worker or new runtime grant is introduced. Existing associations are backfilled from their most recent approved workout membership; their original matching revision was not recorded and cannot be reconstructed. New links pin it explicitly.

Completion backfill retains existing timestamps. Pinned links whose first completion equals the activity start are classified as matching-derived; differing/manual completion timestamps are preserved. Previously unlinked records from an older matching implementation have no source provenance and cannot safely be distinguished from manual completions, so the migration preserves them conservatively. Review any such known historic corrections separately rather than guessing or rewriting immutable timestamps.

The migration takes a table lock while adding the column/constraints and updating existing linked rows. It preserves existing records and permanent history locks. Follow the guarded migration sequence in [database operations](database-operations.md), with a normal backup/restore point before production changes. For recovery, roll the application back and leave the additive column in place; do not delete immutable history or reverse the backfill in production. The old application can ignore the nullable reference.
