# Garmin Data Import (RUN-76 / RUN-77)

Settings offers independent Daily summaries, Sleep and Activities choices. Activities imports only stage 1, Activity summaries. Stage 2, Normalized laps, is an inert Not started placeholder. A completed summaries checkpoint appears as Summary complete � Laps pending; the whole Activities import is not presented as completed. RUN-26 recent activity sync never marks that historical stream completed. The coordinator dispatches stream adapters and uses one bounded checkpointed work loop for date batches and activity offset pages. Daily and Sleep each use a separate owner and connection scoped `sync_cursors` checkpoint (`GARMIN_IMPORT_DAILY_SUMMARY`, `GARMIN_IMPORT_SLEEP`) with a generation, fixed athlete-local start/end, newest-to-oldest next date, failed dates and last checked date. The history duration comes from `GARMIN_HISTORY_YEARS`; saved window boundaries remain valid when that configuration changes, within a separate 20-year safety ceiling. Contiguous verified `summary_fetched_at` or `sleep_fetched_at` rows seed progress, but existing rows alone never declare a new import complete. Checked-empty dates count as coverage. When a populated Daily range omits dates, the importer checks a shorter, at most 30-day range before falling back to one day; only an explicitly empty successful range checks its dates as empty. A successful Daily response with either `[]` or `{ data: [] }` checks the requested date without a measurement. Unresolved dates retain a safe response-shape reason in the checkpoint so Settings can explain why verified coverage did not advance. Reimport resets only the chosen source's checkpoint and upserts valid data without clearing prior valid measurements.

`GARMIN_DAILY_BATCH_DAYS` can be set to 1–365 (default 365); `GARMIN_SLEEP_BATCH_DAYS` can be set to 1–30 (default 30). Each request stops new dates after 22 seconds and uses the existing per-user Garmin import limit, cross-stream provider lease, bearer session and provider Retry-After pause. A later request starts at the next unprocessed date. Retry failed dates only rechecks those dates. The Settings import API dispatches only the chosen stream; Activities uses its own historical and recent checkpoints. The existing RUN-26 activity sync remains available through its own route. Settings counts checked dates for Health sources and never assigns an activity-history percentage.

RUN-24 manual activity import now uses the same provider lease. RUN-26 verifies the Garmin account on the first activity page of each bounded run, then reuses that result only while the saved account and credential nonce remain identical; a new run verifies again. Its activity pages never advance Daily or Sleep historical checkpoints.

The Daily Summary HTTP reader permits up to 4 MiB of JSON while other Garmin JSON calls retain the shared 512 KiB limit. A read-only check on 2026-11-10 found that a 365-day Daily response was 894,536 bytes, above the old limit. Oversized or unparseable range responses stop the run and retain its checkpoint; they are not recorded as failures of individual dates.

There is no configured production Cron. One page request processes one bounded chunk; Settings automatically sends the next owner-scoped request while the page stays open. For HTTP 429 or a saved Garmin provider pause, the first wait is at least 60 seconds and doubles after each consecutive limit up to one hour. A later server-provided Retry-After always wins; the adaptive delay resets after a non-rate-limited response. Other transient failures stop after three consecutive attempts without progress. Terminal account errors and Stop also end the browser loop. Failed Health dates are retried in bounded chunks until they are checked or a retry stops reducing the unresolved count. Closing the page stops further requests; a saved checkpoint can be resumed later. The existing secret-authenticated internal trigger currently schedules the RUN-26 activity importer only. No hosted trigger, approval flag or production schedule was activated for RUN-76. The new state uses existing `sync_cursors`, `sync_runs` and `daily_health_metrics.raw_metadata`; no schema migration or data backfill is required. The latter stores only versioned, allowlisted, bounded metric fields, not provider IDs, GPS, raw payloads or credentials. Deploy the code after the existing RUN-25/RUN-26 migrations. Rollback leaves the new cursor rows and projections inert; imported measurements remain in place.

Health page Sync now requires both Health historical checkpoints to finish, including an explicit completed-with-warnings state. Its first incremental window starts from the earlier of the two import end dates plus one day, with a seven-day overlap. Later windows catch up from the last checked Health checkpoint, bounded by the same three-calendar-year history limit. Activities are irrelevant to this gate. Navigation and charts still read Neon only. The older [Health](garmin-health.md) and [activity sync](garmin-sync.md) documents describe their RUN-25/RUN-26 behavior before this coordinator.

## Activity summaries (RUN-77)

The historical adapter uses the same configured calendar-year, athlete-local window as Health, ending yesterday. It reads the activity-list endpoint for every sport and reuses RUN-24 owner/provider/account/activity-ID upserts. It requests up to 1000 rows per page for the entire remaining historical date range, processes up to three pages per invocation within the shared 22-second budget, and retains the provider's actual returned page length rather than assuming a short page ends history. No activity detail, FIT download or lap normalization is performed. Sparse summaries preserve existing non-null metrics. Existing FIT laps and their check timestamp are retained only when the merged summary is unchanged; a changed summary invalidates old laps and clears FIT freshness so a later FIT-capable importer cannot skip the corrected download. Available distance, duration, elapsed/moving time, speed, heart rate, running cadence, elevation, calories and activity titles use existing canonical storage; unsupported extra list metrics are not persisted. No schema migration is required.

`GARMIN_IMPORT_ACTIVITIES` stores the fixed window, timezone, generation, current range/offset, page count, imported-ID counts and bounded ID sets for verification. Version 2 checkpoints cover all remaining dates in one range instead of splitting history into 30-day requests. Version 1 checkpoints are upgraded on Resume: already verified dates, imported IDs/counts, generation and page count are preserved, while the old range-specific offset and verification state restart at zero for the expanded remaining range. Completed imports stay completed. Search dates are padded by two days and rows are filtered by the saved athlete timezone, covering source-local/athlete-local date differences without assigning an invented source timezone. Each full response is validated before writes. Records are saved in provider offset order so a run nearing its time budget can checkpoint a processed prefix and resume at the exact next offset, without skipping the rest of a large response. A range advances only after two consecutive complete ID traversals match, each ending with an explicit empty successful page. Repeated or overlapping pages cannot duplicate rows or imported counts. An import-wide ID set also prevents double counting when an edited activity moves between date ranges. Changing results trigger another pass; more than four verification restarts, 100,000 traversed rows/IDs per pass or imported IDs in one generation, malformed responses or summary JSON exceeding 8 MiB stop at the saved checkpoint for attention. These bounds are application safeguards, not asserted Garmin limits. Summary counts describe distinct IDs imported on checkpointed pages, including previously imported records later absent from the provider.

Reimport resets only Activities history and updates old activity summaries without resetting Sleep or Daily. Resume and Retry summaries continue the current unverified page. The existing cross-stream provider lease, per-owner attempt limiter, Retry-After pause, account verification and credential-snapshot guards apply to summaries and empty-page checkpoints. Initial checkpoint creation/reset locks the verified credential connection, then fences and locks the provider lease in the same transaction. Rotation, disconnect or lease replacement before that transaction rejects the stale request without overwriting a newer generation. In-flight coverage writes retain their credential and lease guards.

After historical summaries finish, Settings Sync now uses a separate `GARMIN_IMPORT_ACTIVITIES_RECENT` checkpoint. Its first window catches up from the historical end with a seven-day overlap; later windows start at the last fully checked recent end with the same overlap, bounded by the central history configuration. It includes today and does not re-fetch three years on every click. Historical coverage stays independent of recent success or failure. Provider deletions do not delete local records. Edits older than the overlap require an explicit Reimport. Offset traversal cannot prove an atomic Garmin snapshot during continuous upstream edits; consecutive matching ID traversals are the bounded consistency check, and old metric-only edits outside recent coverage remain a reimport limitation.

Tests use synthetic summaries and mocked HTTP responses, including 62 activities, capped and overlapping pages, changed datasets, empty histories, account errors and rate limits. The 62-record synthetic case completes the entire three-year history in four search requests (two full traversals ending in empty pages), instead of checking dozens of monthly ranges; a separate 1025-record case covers the 1000-row page boundary. The request size is an application choice supported by the supplied Garmin sample, not a guaranteed provider maximum. Short provider-capped pages still require a later empty page. Database coverage is part of the existing opt-in `pnpm test:db` suite; tests never contact Garmin.

A downstream `TOKEN_REJECTED` bearer failure is transient: it preserves the current checkpoint, applies backoff and permits Resume/Retry with a newly exchanged bearer. It does not tell the athlete to replace a valid API key or reset historical coverage. Invalid keys and account/permission failures still require attention.

After reload, Settings reads owner-scoped progress every five seconds while a stream or recent sync reports Running without a local import loop. Polling only uses the no-store GET endpoint, stops when the saved state changes or the component unmounts, and is aborted when a local import starts. A late GET cannot overwrite the local action response. This reveals Resume or completion when an earlier request finishes or its lease expires; polling never starts provider work.
