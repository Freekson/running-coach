# Garmin Data Import (RUN-76)

Settings offers independent Daily summaries and Sleep choices. Activities is visible but disabled, with no selection, import action or expandable details. TODO: implement the Activities historical adapter in a follow-up issue. RUN-26 recent activity sync never marks that historical stream completed. The coordinator dispatches stream adapters and uses one bounded checkpointed work loop for date batches or future offset pages. Daily and Sleep each use a separate owner and connection scoped `sync_cursors` checkpoint (`GARMIN_IMPORT_DAILY_SUMMARY`, `GARMIN_IMPORT_SLEEP`) with a generation, fixed athlete-local start/end, newest-to-oldest next date, failed dates and last checked date. The history duration comes from `GARMIN_HISTORY_YEARS`; saved window boundaries remain valid when that configuration changes, within a separate 20-year safety ceiling. Contiguous verified `summary_fetched_at` or `sleep_fetched_at` rows seed progress, but existing rows alone never declare a new import complete. Checked-empty dates count as coverage. When a populated Daily range omits dates, the importer checks a shorter, at most 30-day range before falling back to one day; only an explicitly empty successful range checks its dates as empty. A successful Daily response with either `[]` or `{ data: [] }` checks the requested date without a measurement. Unresolved dates retain a safe response-shape reason in the checkpoint so Settings can explain why verified coverage did not advance. Reimport resets only the chosen source's checkpoint and upserts valid data without clearing prior valid measurements.

`GARMIN_DAILY_BATCH_DAYS` can be set to 1–365 (default 365); `GARMIN_SLEEP_BATCH_DAYS` can be set to 1–30 (default 30). Each request stops new dates after 22 seconds and uses the existing per-user Garmin import limit, cross-stream provider lease, bearer session and provider Retry-After pause. A later request starts at the next unprocessed date. Retry failed dates only rechecks those dates. The RUN-76 import API rejects Activities actions until that stream is implemented. The existing RUN-26 activity sync remains available through its own route. Settings counts checked dates for Health sources and never assigns an activity-history percentage.

RUN-24 manual activity import now uses the same provider lease. RUN-26 verifies the Garmin account on the first activity page of each bounded run, then reuses that result only while the saved account and credential nonce remain identical; a new run verifies again. Its activity pages never advance Daily or Sleep historical checkpoints.

The Daily Summary HTTP reader permits up to 4 MiB of JSON while other Garmin JSON calls retain the shared 512 KiB limit. A read-only check on 2026-11-10 found that a 365-day Daily response was 894,536 bytes, above the old limit. Oversized or unparseable range responses stop the run and retain its checkpoint; they are not recorded as failures of individual dates.

There is no configured production Cron. One page request processes one bounded chunk; Settings automatically sends the next owner-scoped request while the page stays open. For HTTP 429 or a saved Garmin provider pause, the first wait is at least 60 seconds and doubles after each consecutive limit up to one hour. A later server-provided Retry-After always wins; the adaptive delay resets after a non-rate-limited response. Other transient failures stop after three consecutive attempts without progress. Terminal account errors and Stop also end the browser loop. Failed Health dates are retried in bounded chunks until they are checked or a retry stops reducing the unresolved count. Closing the page stops further requests; a saved checkpoint can be resumed later. The existing secret-authenticated internal trigger currently schedules the RUN-26 activity importer only. No hosted trigger, approval flag or production schedule was activated for RUN-76. The new state uses existing `sync_cursors`, `sync_runs` and `daily_health_metrics.raw_metadata`; no schema migration or data backfill is required. The latter stores only versioned, allowlisted, bounded metric fields, not provider IDs, GPS, raw payloads or credentials. Deploy the code after the existing RUN-25/RUN-26 migrations. Rollback leaves the new cursor rows and projections inert; imported measurements remain in place.

Health page Sync now requires both Health historical checkpoints to finish, including an explicit completed-with-warnings state. Its first incremental window starts from the earlier of the two import end dates plus one day, with a seven-day overlap. Later windows catch up from the last checked Health checkpoint, bounded by the same three-calendar-year history limit. Activities are irrelevant to this gate. Navigation and charts still read Neon only. The older [Health](garmin-health.md) and [activity sync](garmin-sync.md) documents describe their RUN-25/RUN-26 behavior before this coordinator.
