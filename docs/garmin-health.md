# Garmin daily health history (RUN-25)

## Sleep stage summary display

The Health page now uses four semantic stage colors: light `--color-sleep-light`, deep `--color-sleep-deep`, REM `--color-sleep-rem`, and awake `--color-sleep-awake`. A daily duration bar stacks these totals from bottom to top in that order when all four verified values are present and their asleep sum agrees with `sleepTimeSeconds` within five minutes. Older or incomplete nights retain a neutral total-duration bar; missing dates remain gaps. The chart shows daily stage totals in hours, not a timeline within the night. The inspected Personal API responses did not include timestamped `sleepLevels` or equivalent stage intervals, so no hourly stage sequence is inferred.

The importer also saves `sleepScores.overall.value` and the GMT sleep end timestamp when valid. `20261110_garmin_health_identity` adds five nullable sleep-stage columns to `daily_health_metrics`; existing rows are untouched, and the existing nullable `sleep_score` column is reused. Deploy that migration before the code that reads the new columns. The short `ALTER TABLE` needs a table lock but no backfill. On rollback, leave the columns in place until the new code is retired; dropping them would discard newly collected stage history. Historical rows without stages become segmented only if Garmin later rechecks those dates. The Health page continues to read Neon only; period and score toggles make no Garmin requests.

The adapter treats zero resting HR or sleep duration as an absent measurement. The snapshot distinguishes dates never checked, dates checked with no verified value, and sleep dates whose requests failed. A failed request never creates a fabricated sleep value or a success fetch timestamp.

The protected `/app/health` page reads its snapshot and 90-day chart source from Neon. Its 7/30/90-day period selector filters those persisted rows in the browser and never contacts Garmin. Missing dates remain gaps. A seven-day average appears after at least three valid observations for that metric; the date shown beside a reading is its measurement date, while sync status uses the request completion date. Settings keeps Garmin key management; Training contains activity sync controls. Health measurements stay on the Health page. Health has a single **Sync now** action. The first sync checks at most 30 local days including today for the active Garmin credential. Later syncs recheck the latest seven days, including sleep that Garmin may publish late. If more than seven days were missed, the saved window end drives bounded catch-up before the recent overlap. Each leased request processes up to ten days within a time budget and commits its next day to a `HEALTH` SyncCursor. The client automatically continues up to three bounded requests from one click. A completed same-day window has a one-hour manual cooldown; interrupted windows may resume under their retry policy. This reuses RUN-26's cursor, run, lease and provider pause patterns and the shared Garmin import rate limit; it adds no scheduler or polling job. Hosted use remains behind the Garmin approval gate.

A saved development credential from before stable account association may have no `externalAccountId`. Settings labels it **Verification needed** instead of claiming the first import is pending. Health offers **Verify & sync**: the server verifies the stored key's account ID, binds it only if the credential nonce is still current, and then begins the bounded import. A failed or unverifiable account check imports nothing. Existing records without verified provenance remain hidden and are never assigned to the newly verified account. Settings refreshes the client route after a key change so the Health and Training state can be re-read from Neon.

The Garmin request limit is shared with activity sync: an owner may start at most three import requests in a 60-second window. A fourth request receives `APP_RATE_LIMITED` and the next eligible time. Attempt reservations lock and require an active Garmin connection; a stale request cannot recreate rate-limit state after imported Garmin data is deleted. A provider `429` uses the provider retry time and reports `PROVIDER_PAUSED`. A different import failure can also pause the health cursor for a bounded retry; the UI describes that as a retry wait rather than attributing it to Garmin. A failed sleep read is classified as timeout, network, HTTP status, invalid response or date mismatch, without recording response bodies. The response contains only a safe code and retry time, never a key or raw health payload.

The server prefers the athlete profile's saved `preferredTimezone`; when absent or invalid, the browser supplies its IANA timezone as a fallback. For each historical day, a matching Garmin activity imported under the current key can supply a timezone, then an already stored health timezone, then the effective fallback. A previously stored sleep timezone remains independent of the summary timezone even when both zone names happen to match. `source_timezone_basis` and `sleep_timezone_basis` record whether a zone was inferred from activity, profile, browser, a stored value or a direct request. **None of these is a Garmin-verified daily-health IANA timezone.** Travel days without a dated activity or stored zone cannot be inferred from the current profile/browser zone alone. Date arithmetic advances calendar dates in UTC, while `Intl.DateTimeFormat` determines the day in the selected IANA zone. Local sleep timestamps are never reinterpreted as UTC instants.

Each leased invocation reads one Daily Summaries range and one Sleep Summaries range for its next bounded chunk of at most ten dates. Only a unique, valid top-level calendar date can assign a range record to a day. A valid daily summary with no resting value is checked-empty; a missing, duplicate or malformed summary gets a single-day fallback. Only an empty `data` array on the single-day summary endpoint is checked-empty; a nonempty malformed array remains unresolved. A sleep range record is accepted only with an unambiguous date and valid positive duration. Undated, duplicate, malformed or empty sleep range records get a single-day fallback. A failed sleep range request also leaves its dates unresolved for single-day fallback, except when Garmin has requested a rate-limit pause. A single-day sleep object is checked-empty only when its required date, duration and start/end timestamps are explicitly null, all sleep measurements are null, and any non-null fields are limited to verified sleep-need metadata (`sleepNeed`, `nextSleepNeed`, `deviceRemCapable`, `retro`). A separately authorized two-request check on 2026-11-10 confirmed that Garmin returns this metadata-bearing empty shape for an unmeasured date. HTTP 204 is also checked-empty; HTTP 200 with a null body, a dated record without a positive duration, or unexpected non-null content remains a failure. Pending sleep retries remain single-day reads. Range payloads are kept only in the invocation's memory and are not persisted or logged.

With complete dated range responses, the first 30 days use three leased invocations and 12 Garmin HTTP requests: one token, one legacy daily-summary account check and two range reads per invocation. A seven-day refresh uses one invocation and four requests. Verifying a legacy saved key without an account ID adds one token and one daily-summary account check to the first user-initiated sync. Each unresolved date can add one single-day read per source. The existing 22-second invocation budget can end a chunk early, and the three-attempt application rate limit can prevent further automatic continuation from the same click. The checkpoint preserves remaining dates for the next eligible sync.

The importer maps verified `heartRate.restingValue` in bpm and `sleepTimeSeconds` converted to milliseconds. Missing values remain `null`. HRV, Body Battery, steps and weight are not ingested until their Personal API units or meaning are verified in ADR-002. A verified Garmin health row is unique by owner, provider, athlete-local date and stable Garmin `userProfileId`. Its encrypted-key nonce is retained only to guard writes against an in-flight key replacement. Same-account key rotation preserves rows and checkpoints. Disconnecting removes the key and stops sync while leaving verified rows visible. Historical rows without verified account provenance remain stored but hidden and are never silently merged. Summary and sleep retain separate IANA zones; the two retrieval timestamps distinguish checked-empty from not fetched. A checked-empty recheck updates its source timestamp and attempt sequence without clearing an already stored measurement or its timezone. An atomic per-owner attempt sequence prevents older responses from overwriting newer ones. A failed sleep read after a successful summary returns `PARTIAL`, and retry skips already fetched sources. One bearer token is reused within a bounded invocation, with one refresh on a downstream `401`. Raw provider responses are discarded.

When a single-day sleep read fails, the checkpoint records that date in `sleepRetryDates` and `sleepFailedDates` without inventing a measurement. A timeout, network error or sleep HTTP failure opens a circuit for the rest of that bounded invocation: remaining dates fetch summaries only, and the run applies bounded backoff. An invalid or mismatched single-day sleep record stays unresolved but does not block later dates from fetching sleep. Each invocation tries a failed date at most once, and at most two pending sleep retries are prioritized before fresh dates so an older malformed date cannot starve new history. The client continues bounded requests from one Sync now action and shows a toast when unresolved sleep dates remain. Successfully fetched summaries are not downloaded again on sleep-only retries. Completion requires both the calendar cursor and the pending sleep list to be empty. Dates that age past the 30-day import horizon become visible gaps rather than trapping the cursor; still eligible dates are retried. The UI marks an attempted failed sleep date as `Request failed` and later deferred dates as `Not checked`. HTTP 204 or a verified metadata-bearing empty single-day sleep object marks sleep checked with no data; HTTP 200 with a null or empty body and malformed nonempty JSON remain failures. No health scheduler or navigation-triggered Garmin request was added.

The Health page's expanded Garmin sync details contain a diagnostic log of the five most recent owner-scoped health runs and rejected health requests. It shows local start time, result, processed date count for actual runs, allowlisted internal error code and HTTP status when encoded in that code, plus the retry time when available. Unresolved sleep errors from a completed partial run are retained on that run. A failed Sleep Summaries range request followed by successful single-day fallbacks is saved as a recovered API error on the run, so the diagnostic log still shows the upstream failure. Pre-run failures such as application rate limits and saved-key identity verification use a separate `GARMIN_HEALTH_REQUEST` job type; ordinary repeated errors of the same code within a minute are coalesced on a best-effort basis, and these diagnostic entries never affect the sync checkpoint or status. The log does not store or display provider response bodies, credentials, personal measurements or arbitrary error text. Older runs remain in the existing `SyncRun` table but are not loaded into the page.

`getHealthSnapshot(owner)` in `src/server/health/history.ts` is the reusable owner-scoped Health/dashboard selector. `HealthSnapshot` in `src/components/health/HealthSnapshot.tsx` displays each metric's own observed date, unit, source and older-reading state. The older-reading threshold uses the metric's source timezone and a fixed render instant, so it stays accurate across UTC midnight and matches between server and client rendering. RUN-43 can reuse both without importing health data on dashboard load. `getHealthTrendRows(owner, startDate, endDate)` supplies the Health page's persisted chart data; the Health page loads all stored dates for its owner and verified Garmin account. `HealthHistoryPanel` renders accessible line and bar charts with separate 7D, 30D, 90D, 1Y and All controls for heart rate and sleep. The 1Y and All charts show weekly averages over available measurements and keep weeks without readings as gaps. Changing a period reads in-memory Neon data and never calls Garmin.

Deploy `20261110_garmin_health_identity` before the code. It adds nullable provenance, sleep-stage and account columns to `daily_health_metrics`, an account column to `activities`, and a non-null, zero-default attempt counter to `garmin_import_rate_limits`; it does not rewrite existing readings. Each table receives a short lock for `ALTER TABLE`; no data backfill is needed. Older health rows have unknown retrieval time and attempt order and do not appear as verified snapshot readings. On application rollback, leave the new columns in place until a later migration; dropping them would lose fetch coverage and sleep-start provenance.

The same migration adds a stable account ID to activities and health rows, account-scoped uniqueness and a partial global unique Garmin connection index. Existing activities receive `LEGACY_UNVERIFIED`; older health rows keep a null account ID. Neither is attributed to a newly connected account. The 15 earlier tracked migrations retain their names and checksums; the four previously untracked Garmin migrations were combined into this one before release. No production migration was run.

After an absence longer than 30 days, catch-up starts at the oldest date in the current 30-day window. Earlier dates remain visible gaps because this importer does not request older history. Date validation uses the timezone that selected the sync window, allowing a different source zone on a travel day without expanding the selected 30 dates or accepting future dates.

## Detailed daily heart rate follow-up

Garmin's [official Personal API Python client](https://github.com/garmin/connect-personal-api-python#endpoint-wrappers) lists `GET /wellness-service/wellness/dailyHeartRate?date={calendar_date}`. That establishes a documented single-date request shape, not the response's field types, sample timestamps, sampling interval, coverage or missing-value rules for our account. The repository PoC has no verified `dailyHeartRate` response fixture, and the publicly reachable [Personal Swagger page](https://developer.garmin.com/gc-developer-program/personal/swagger-docs/) did not expose a usable schema in this review. Intraday ingestion needs an authorized, bounded structural probe and unit/timestamp validation before adding a parser or chart. RUN-25 therefore uses the verified daily-summary resting HR only; it does not poll or claim continuous heart-rate data.

The activity sync checkpoint now persists a newly selected window under its lease before the first provider request. A timeout or `429` on the first extension page therefore leaves the older requested window in progress for a later ordinary sync. Both Garmin import paths honor provider retry pauses up to 30 days, capping excessive `Retry-After` values so they cannot block a user's imports indefinitely.
