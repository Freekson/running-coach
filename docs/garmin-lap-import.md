# Garmin normalized lap backfill (RUN-78)

[RUN-78](https://linear.app/fr-running-coach/issue/RUN-78/backfill-normalized-garmin-fit-laps-for-imported-activities) enables the second Activities stage in Settings after RUN-77 summaries finish. Recent activity synchronization is available on Training; Settings provides historical import, resume, retry and explicit reimport controls. Every imported Garmin sport is eligible within the saved athlete-local history and recent-sync windows. GET progress requests are read-only.

## Durable work and ownership

`activities.fit_import_state` records `PENDING`, `RUNNING`, `COMPLETE`, `FAILED` or `UNAVAILABLE` for each owner/account/activity. Error code, attempt count, per-item cooldown and the existing `fit_checked_at` preserve retry evidence. Failed IDs are the activity rows themselves; no provider payload is saved in the checkpoint. `GARMIN_IMPORT_ACTIVITY_LAPS` has its own `SyncCursor` lease, cooldown, last-sync time and `SyncRun` records. Counts come from the scoped database rows, including after reload.

POST accepts `streamId: activities` and `stage: laps`; it never accepts a user ID or an activity ID. The verified session determines the owner. The server selects work by owner, active Garmin account and athlete-local window. The account is checked before a selected activity is bound to downloaded data. Credential nonce, provider lease, stage lease and the activity snapshot are fenced before writes. Replacing credentials or a lease prevents an older response from completing work.

The stage shares the existing Garmin limiter and provider lease with all other imports. Each invocation processes up to ten files sequentially within a 22-second work budget; requests and decoding also have individual deadlines. Each activity commits independently. Interrupted `RUNNING` rows are reclaimed only by the next fenced invocation. The browser requests further batches only while Settings remains open. There is no new background scheduler. A paused legacy recent-sync checkpoint does not prevent lap work once historical summaries are complete; that checkpoint remains unchanged.

Normal import/resume processes pending rows. `Retry failed FITs` processes only failed rows whose cooldown has expired; each attempted failure receives a new cooldown if it fails again. 429 pauses provider work using Retry-After. When the last item in a failed-only retry is interrupted by 429 or a temporary bearer rejection, Settings waits through the saved backoff and retries it while the page stays open. Stop/unmount cancels continuation. Rejected temporary bearer tokens are resumable; an invalid API key, account mismatch or denied access requires attention. Per-file 5xx, network errors and corrupt FITs become retryable failures without blocking other files. Missing downloads, size limits and valid files without supported lap data become explicit terminal unavailability.

Overall Activities completes only after summaries and laps complete. Terminal unavailability produces `Completed with warnings`; retryable failures keep the stage unresolved. Reimport summaries uses `summaryRetryAfter`, which includes only its own checkpoint cooldown and the shared provider pause; individual failed-FIT cooldowns continue to block only lap retry/resume controls. An unchanged summary reimport preserves complete lap work. A changed canonical summary invalidates its old FIT evidence and schedules that activity again. A future targeted refresh can explicitly reset selected owned rows to `PENDING`; summary reimport does not serve as a blanket FIT refresh.

## Binary validation and compact metrics

Download responses are bounded to 8 MiB and identified by content. ZIPs allow at most 32 entries and 8 MiB of combined uncompressed content. The decoder rejects encrypted/multi-disk/ZIP64 archives, unsafe paths, symlinks, overlapping entries, conflicting headers, CRC/size mismatches and ambiguous FIT payloads. Raw FIT integrity and exact file length are checked before decoding. Decoding has a five-second deadline and 100,000-message cap; normalization accepts at most 10,000 laps.

FIT must identify an activity with valid session bounds. Its start, available distance and elapsed duration are checked against the server-selected summary. Session and lap end times are calculated as `start_time + total_elapsed_time` for both summary-first and summary-last files. The message `timestamp` is the write time and must not be used as an interval endpoint; see [Garmin's FIT summary-time clarification](https://forums.garmin.com/developer/fit-sdk/b/news-announcements/posts/important-fit-activity-file-message-change). Ordered lap bounds, elapsed-duration totals, overlap and session-distance totals are validated before canonical persistence. List `splitSummaries` and `lapCount` never create lap rows. Missing metrics remain null. A valid session explicitly declaring zero laps can complete with zero rows; absent lap messages alone do not prove zero.

Persisted lap metrics include UTC start/end, distance in meters, elapsed/timer durations in milliseconds, average/max HR in bpm, average/max speed in m/s, average/max power in watts, cadence in cycles/minute, and ascent/descent in meters. FIT timer time is stored separately; it is never mislabeled as moving time. Generic cadence is never implicitly converted into running steps. Existing steps/minute and moving-time fields remain null unless explicitly supported by their source.

Training incremental FIT refreshes and Settings backfill use the same complete canonical lap metric mapping, so refreshing an unchanged FIT preserves its richer metric columns. A confirmed zero-lap session may coexist with other sessions containing laps; unknown missing coverage and contradictory zero-lap declarations remain invalid.

Lap replacement and per-item completion share one transaction and retain stable lap IDs where source identity is unambiguous. Empty or broken refreshes cannot erase a previously valid breakdown. Summaries and their source observation order are not rewritten by lap persistence. FIT/ZIP bytes, records, events and precise GPS streams remain transient server memory; none enter the database, browser response or logs.

## Migration and recovery

`20261112090000_run78_normalized_lap_backfill` is additive: four work-state columns on `activities`, an owner/account/work index, and nine nullable compact-metric columns on `activity_laps`. Existing imported/retained lap breakdowns become `COMPLETE`; other rows start `PENDING`. Owner-compatible foreign keys and uniqueness remain unchanged. State/attempt and nonnegative metric checks reinforce runtime validation. Existing table grants continue to apply; no new table or role is introduced.

Deploy the migration before code that queries the new columns, then regenerate Prisma and deploy the application through the existing guarded release workflow. ALTER TABLE, the backfill UPDATE and index creation take normal table/index locks; plan the release around the current table size. No athlete data is dropped. Recovery is to restore the previous application while retaining the additive columns; do not drop lap data to recover a failed import. A production backup and normal release approval remain the operator's responsibility.
