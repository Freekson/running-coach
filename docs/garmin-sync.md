# Garmin activity synchronization (RUN-26)

The authenticated Training action calls `POST /api/integrations/garmin/sync`. A call processes at most four search pages of one activity per page by default and stops starting new pages after 20 seconds. The defaults are a seven-second request timeout and one-second pacing. `GARMIN_SYNC_MAX_PAGES` (1вЂ“4), `GARMIN_SYNC_PAGE_SIZE` (1вЂ“2), `GARMIN_SYNC_RUN_BUDGET_MS` (5,000вЂ“20,000), `GARMIN_SYNC_TIMEOUT_MS` (3,000вЂ“7,000) and `GARMIN_SYNC_PACING_MS` (1,000вЂ“2,000) may tune these within the hard caps. Requests remain sequential per owner. The serverless route is capped at 60 seconds. Each click is also subject to the existing shared database rate limiter of three Garmin import attempts per minute. The UI reports processed activity counts and the next date, rather than a percentage.

The first window is 84 calendar days (12 weeks) ending today. `GARMIN_INITIAL_IMPORT_DAYS` may lower this to 7вЂ“84 days. After the window completes, another normal sync revisits the most recent seven days to pick up amendments. If a backfill or older extension finishes more than seven days after the last completed recent window, sync first catches up the missing dates in seven-day windows. The checkpoint retains the most recent completed date across older extensions; an older checkpoint without this field is conservatively re-scanned from its last window end. The user can explicitly request a further seven older days from Training; the API accepts a bounded `extendDays` value of 1вЂ“28 only after the current window completes. A successful empty page advances that date only. It says nothing about Garmin's historical coverage.

`sync_cursors` holds the exact date and offset after a completed page. When the run deadline is near, a two-activity search page may return after the first saved activity and checkpoint its next offset; the remaining activity resumes on the next run. Paginated dates retain seen Garmin IDs and get a verification scan from offset zero before the cursor moves to the next date. If that scan finds a new ID after the list shifts, the date is scanned again. Each request remains page and time bounded; a continually changing date stays in progress. The activity and lap importer upserts by owner, provider, external ID and verified Garmin account ID. A crash after importing an activity but before advancing the cursor replays that page safely. The cursor row has a 100-second lease with an unguessable token. Only the current lease holder may commit progress. An expired lease can be reclaimed; its old `sync_runs` row is marked interrupted. An invalid saved checkpoint records a failed run and is held for an hour before retry, allowing other owners to be scheduled. Same-account key rotation invalidates the in-flight lease but preserves its checkpoint; disconnecting removes the cursor and stops sync. A fetched activity is saved only while the same credential is still active, with the connection locked for the short persistence transaction. Saved activities are retained.

The existing key vault exchanges the user-owned encrypted Garmin key for a short-lived access token on demand. Before searching or persisting activities, each bounded page checks the legacy Daily Summary `userProfileId` against the saved account association. A missing or mismatched ID fails closed. No refresh-token flow or token persistence is added. Historical backfill skips a repeat FIT download when a saved activity has imported laps or a FIT check within the last 24 hours, provided its JSON summary is unchanged. Incremental, extension and explicit manual imports recheck unchanged FIT laps or a missing FIT after 24 hours using the nullable owner-scoped activity `fit_checked_at` timestamp; a successful FIT read or definitive missing-file response advances that timestamp with the activity write. If the JSON summary changes and FIT fails transiently, the old timestamp is cleared so the next attempt fetches FIT again. New activities request FIT for laps. The search result is treated as an ID list; details are still fetched for new or changed activity data because the verified search summary does not establish the complete canonical detail contract. Neither a missing historical activity nor a changed activity older than the seven-day overlap is inferred from a successful incremental pass. Deletions are not automatically reflected; an older correction needs an explicit bounded extension or later manual handling.

The importer records progress only after the activities included in that checkpoint are stored. A FIT 408 or other unrecognized FIT status can save verified JSON, but leaves the checkpoint in place for retry rather than treating missing laps as a completed page. Requests share a run deadline; if it expires during an activity, the uncommitted page is retried from the saved checkpoint. A `429` uses the full valid `Retry-After` when present, otherwise bounded exponential delay with jitter. The per-owner provider pause is shared with the older manual import route and the prepared scheduled trigger. Replacing the key clears its previous pause. Token-endpoint key rejection requires a replacement key; a downstream `401` is retryable because the short-lived token may have expired. A downstream `403` requires a permission check but does not label the saved key invalid. Other errors retain the checkpoint. Training refreshes paused and active states while the page stays open. Errors and run summaries contain codes and counts only; keys, tokens, raw health data, GPS and FIT bytes are not logged.

## Dashboard incremental sync (RUN-43)

Dashboard reads persisted sync state without contacting Garmin. Its **Sync now** action sends one bounded request per eligible stream (`activities`, `daily_summary`, `sleep`) to `/api/integrations/garmin/incremental-sync`, in sequence. Every request derives the owner from the verified session, checks the same-origin JSON body, and dispatches `action: sync` through the RUN-76 registry. It cannot request an import, reimport, extension, or historical lap job.

Activities reuse the recent summary traversal and `GARMIN_IMPORT_ACTIVITIES_RECENT` checkpoint. Daily summary and sleep reuse the RUN-25 Health worker with explicit source selection and independent `GARMIN_HEALTH_RECENT_DAILY_SUMMARY` and `GARMIN_HEALTH_RECENT_SLEEP` cursors/jobs. The existing Health page's combined `HEALTH` cursor remains supported by the same worker. Source-verified health coverage and idempotent writes remain in the existing importer; no schema change is needed. Historical cursors are read to establish initial-import completion and are never reset or advanced by this action.

An unfinished initial import is skipped independently and links to **Settings → Garmin Data Import**. Each eligible stream keeps its own cursor, failure and retry time. All entry points still contend for the existing owner/connection provider lease and share the three-attempt-per-minute limiter and provider pause. A lease race returns busy without starting concurrent provider work. Each stream retains the worker's 22-second work budget, with a 40-second route limit. Opening Dashboard never starts synchronization or historical work. One explicit Sync now click arms a browser session that continues bounded incremental requests until the selected eligible streams finish, while Dashboard stays mounted.

The compact card always displays Activities, Daily summary and Sleep in one row on desktop and stacked on mobile. It uses connection/sync badges and short stream statuses. “Up to date” requires completed incremental coverage with a successful timestamp within 24 hours; a completed historical import, an absent timestamp, and an older sync do not qualify. The header uses the oldest of three stream success timestamps as a conservative last full sync time; when only some streams have timestamps, it explicitly labels the latest one “Last stream sync”.

An inline Retry invokes only the selected failed stream through the same action, preserving unaffected successful results. Health retries use the worker's existing saved checkpoint and failed-date recovery. During an armed session, request-budget exhaustion automatically queues the unfinished stream for another pass; completed streams are removed from the queue. Rate limits wait until at least the saved Retry-After, using the same exponential-backoff and abortable-wait helpers as Settings. All pending streams are rechecked after each wait. Known busy leases use persisted status reads rather than duplicate provider work. The header uses Waiting while a continuation is scheduled; a status tooltip gives its local resume time. It adds no running-status or setup-helper paragraph.

The global Sync now action can arm a session during a known pause and waits before making provider requests. Per-stream manual Retry stays disabled until its saved deadline. Retryable transport errors and server errors with a saved backoff get up to three attempts; credential/permission/checkpoint problems stop and link to Settings. Three repeated unchanged checkpoint markers stop automatic continuation, retaining Incomplete and Continue for manual recovery. Checkpoint markers contain only explicit dates and progress counts, never provider payloads. There are no invented percentages or unsupported server cancellation controls.

Only three recently completed stream results produce an overall success announcement. Partial writes remain visible, and `router.refresh()` reloads persisted dashboard reads after the operation. While another page holds the provider lease, Dashboard polls only the persisted status endpoint until the lease clears. The status snapshot exposes the shared lease separately from per-stream completion, so a single active stream does not erase successful results. Every action rechecks status before dispatching and still enforces the shared owner-scoped lease and limiter on the server.

A failed session attempt remains visible across later status reads and the final page refresh, even if it failed before a durable run was recorded. An older saved success cannot replace that result. Only a completed result confirmed during the session, or a newer persisted success within that session's time window, can confirm recovery. Longer saved retry deadlines remain authoritative when reconciling those results.

The browser keeps the latest attempt and its recovery boundary separately for each stream, scoped to the Garmin connection. Retrying one stream cannot erase another stream's unresolved attempt, and status reads do not replace the attempt history. Later sessions inherit unresolved attempts from the same connection without submitting unrelated stream requests. Each stream retains its original recovery boundary, so a confirmed recovery before a later targeted retry remains valid. The aggregate badge and announcement derive from the reconciled current streams after an operation finishes; confirmed external recovery clears Incomplete. Changing connections ignores the previous connection's attempts and completion announcement.

A bounded pass that saves progress without an error is not a sync failure. An armed session continues it automatically; an interrupted or stalled session retains Incomplete with Continue for the saved stream. Sync issue remains reserved for failed results, connection errors or unavailable status reads. Mobile header actions align to the right edge of the card.

Sessions are browser-owned, not durable jobs. Navigating away or closing the page disarms future requests and timers; an already accepted server request can finish its bounded work. Checkpoints remain saved for the next click. Every continuation carries the original connection ID as a precondition, checked against the verified current owner's connection; changing accounts or connections cannot redirect a waiting session to another user's provider. Server authorization still derives the owner solely from the session. No automatic work is restored merely by opening Dashboard, and no worker/queue, table or migration is added.

## Activity retry recovery

Training's normal Sync now action uses `training-sync.ts`, which delegates to the existing `GARMIN_IMPORT_ACTIVITIES_RECENT` summary traversal and bounded lap stream after Settings summary import is complete. It searches the catch-up range through today, rather than stepping through the legacy `ACTIVITIES` INITIAL cursor. Fresh summaries are saved before FIT work; the UI can continue an incomplete recent traversal once within a click. GET status and Training's initial header state read the same recent streams. The legacy service remains for the scheduled trigger and explicit bounded extension requests. Quota is reserved by each stream, without an extra duplicate reservation in the route.

After recent summaries complete, each request can run one bounded FIT batch within the remaining time budget. Pending downloads take priority; when none remain, Sync now retries failed downloads whose cooldown has expired. Provider pauses and per-activity retry times still apply.

The request reserves up to 50 seconds for work within the route's 60-second limit, starting FIT only when its full 22-second batch budget remains. If summary traversal uses that time, the next request continues the pending/retryable FIT batch using the saved recent coverage. Coverage completed within the last five minutes can be reused for continuation; older coverage is refreshed first so a long FIT backlog does not indefinitely delay new summaries. Each request still starts at most one bounded FIT batch.

Garmin activity details can encode `activityUUID` as `{ "uuid": "..." }` while other responses use a string. The adapter validates and flattens the nested UUID before canonical validation. Synthetic normalizer/importer tests cover this shape; unknown object shapes still fail closed.

Activity parsing, network and timeout failures retain their activity cursor backoff without setting a provider-wide pause. Only an actual `RATE_LIMITED` import failure extends the shared provider cooldown. Sync state reports the latest active provider/cursor retry time and omits expired retry times. The endpoint returns an existing active pause before consuming an application request allowance; denied allowances distinguish `APP_RATE_LIMITED` from `PROVIDER_PAUSED` and return `retryAt` plus `Retry-After`.

Training displays the actual failure reason and local retry time instead of labeling every backoff as a Garmin rate limit. The button unlocks when a known retry time expires even if status polling fails, without automatically sending a provider request. Cross-user isolation, lease claims and provider quotas remain enforced.

## Deployment gate

Authenticated manual sync, health/data imports and FIT charts use the same per-owner credential/account checks, quotas, cooldowns and leases in every deployment environment. No deployment-specific sync approval setting is required. Provider permission scope, conditions and expiry must still be verified operationally before deployment. This repository has **no** `vercel.json` Cron entry. The secret-authenticated `GET /api/internal/garmin-sync` trigger remains opt-in through `GARMIN_SCHEDULE_ENABLED=true` and `CRON_SECRET`, and processes at most one eligible connection per invocation. It shares the three-attempt-per-minute owner limit with manual sync. Completed windows have a one-hour scheduling cooldown; incomplete windows may resume sooner within that shared limit. Action-required checkpoints and connections without a verified Garmin account ID are excluded from scheduled sync. A user can verify a previously saved key from Training with **Verify & import**; the identity is bound only if the saved credential has not changed, then the bounded import begins. Eligible connections rotate by their most recent sync attempt, including failed attempts and never-synced users. Do not enable scheduling or install a production schedule until approval and the actual deployment plan, Fluid compute setting, function duration and trigger frequency have been verified with the owner.

Vercel's [current Cron project limit](https://vercel.com/changelog/cron-jobs-now-support-100-per-project-on-every-plan) is 100 per project, but an account's allowed schedule frequency and this project's plan have not been confirmed. [Function duration](https://vercel.com/docs/functions/configuring-functions/duration) depends on plan and Fluid compute. The 60-second route limit is conservative, but must be checked against the actual project before activating the trigger. [Garmin's Personal API FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq) documents key/token lifecycle but no numeric request quota; the project has not verified a numeric quota or guaranteed historical reach.

Apply `20261108_run26_garmin_sync` only after the guarded development-target assertion. This single migration adds nullable lease/retry columns and one failure counter to `sync_cursors`, nullable `provider_retry_at` to `garmin_import_rate_limits`, and nullable `fit_checked_at` to `activities`. It does not backfill or rewrite existing data. Deploy the migration before the code. Adding `fit_checked_at` takes a short table lock but does not rewrite activity rows. If rolling back the app, keep the nullable columns until sync and manual imports are disabled; removing them then loses in-progress checkpoint, pause and FIT refresh timing, while existing activity and lap data remain separate.

## Garmin account association

The verified legacy `GET /usersummary-service/usersummary/daily?calendarDate=...` response exposes a numeric root `userProfileId`; the sampled v2 range record did not expose that field. Connecting and replacing a key requires that stable ID. The ID is stored on `integration_connections` independently of encrypted credentials and is globally unique for Garmin connections. A different or unverifiable ID leaves the previous key and history untouched. Disconnecting removes credentials but retains the association and verified imported activities and health history. Settings offers a separately confirmed **Delete all imported Garmin data** action that removes Garmin activities (including laps), health rows, sync state and the association; unrelated data remains. An account can change only after that reset. Older records with no proven account ID are isolated and never merged based on measurements or external activity IDs alone.

The account policy and RUN-25 health columns are added together by `20261110_garmin_health_identity`. The 15 earlier migrations remain intact because development and production workflows track their names and checksums. The four previously untracked Garmin migrations were combined before release. No production migration was run.
