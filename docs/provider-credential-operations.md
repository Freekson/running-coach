# Provider credential vault operations (RUN-21)

The vault stores one connection per user and provider in `integration_connections` and one encrypted credential per connection in `integration_credentials`. `OPENAI` and `INTERVALS` API keys use the same server-only service. The OpenAI settings control stores a key for future automatic plan generation; it does not call OpenAI or enable that feature. Manual ChatGPT file exchange requires no key.

## Secret configuration

Set `CREDENTIAL_ENCRYPTION_ACTIVE_VERSION=1` and `CREDENTIAL_ENCRYPTION_KEY_V1` to a separately generated, base64-encoded 32-byte random key in each environment's server-side secret store. For example, generate a value privately with `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"`. Never put the value in source, `.env.example`, GitHub Actions, a browser variable, logs, or Neon. Use distinct keys for local, Preview, and Production. Missing or malformed key material fails credential writes and reads closed; existing ciphertext remains in the database.

AES-256-GCM encrypts each credential with a fresh 96-bit nonce and authenticates the owner ID, connection ID, provider, and API-key type as associated data. The database stores ciphertext, nonce, tag, and key version. Status responses contain only provider, connection status, and timestamps. The API never returns a key after saving it. Deleting a connection's credential disables local reads; it does **not** revoke the key at OpenAI or another provider.

## Rotate vault encryption keys

This procedure changes the app's encryption key. It is separate from a user replacing or revoking a provider API key.

1. Keep the old key configured. Generate a new independent 32-byte key and add `CREDENTIAL_ENCRYPTION_KEY_V2` (or the next numbered version) to the same server-only secret scope. Deploy all active app instances with both keys and `CREDENTIAL_ENCRYPTION_ACTIVE_VERSION=2`. Retire older app deployments before re-encrypting, so no instance continues writing version 1.
2. In a protected operator environment with the target's **direct** `DIRECT_URL`, `APP_DATABASE_ENV` (`preview` or `production` for deployed environments), all historical key versions, and the active version, set `CREDENTIAL_ROTATION_DEPLOYMENT_ORIGIN` to the matching deployed HTTPS origin and `DB_VERIFY_TOKEN` to that deployment's private verification token. Do not copy these values into GitHub or shell history. The deployed `/api/internal/credential-key-verify` endpoint responds only to a token-authenticated random challenge. Its proof binds the app's active and historical keys to the database endpoint, database name, and schema used by the deployment. The operator's `DIRECT_URL` must point at that same target; a restored copy on another endpoint fails verification even if it has the same keys. No key or database URL is transmitted. Remote database writes are refused without this proof.
3. Run `pnpm credentials:rotate --check`. For Production append `--production`; the database's private tier marker must match. The command verifies each stored key version on the deployment when an origin is configured and checks that every stored row can be decrypted with its recorded version. It prints counts only, never IDs or plaintext. Stop if any deployment proof or decryption fails.
4. Run `pnpm credentials:rotate --apply` (append `--production` for Production). It rechecks all required deployment key versions before any write, then conditionally re-encrypts each older row under the active key. Replacements or removals that race the scan are not overwritten. If any row fails, keep all old keys and fix the cause; rerunning is safe for already rotated rows.
5. Run `--check` again with the same deployment origin and confirm **zero** rows remain on older versions, every active-version row decrypts, and the deployed key proof still matches. Only then retire old key versions. Keep backups and their historical keys together under the backup retention policy; a database backup without its matching key cannot restore credentials.

For a first deployment, apply the RUN-21 migration before deploying code that references `OPENAI`, configure version 1, then deploy. The migration refuses existing duplicate `(user_id, provider)` connections instead of deleting credentials. Reconcile such rows privately with their owners before retrying. Creating the unique index briefly locks connection writes; schedule migration during a low-traffic window. No existing ciphertext is transformed by the migration.
